## A. 개념 정확성

### 🔴 A-1. 트리 탭의 휴리스틱이 완전 무작위였음 (가장 심각)

```javascript
let h = (id === this.goalNode) ? 0 : Math.floor(Math.random() * 20) + 1;
```

h(n)은 "목표까지 남은 거리의 추정값"인데 1~20 난수를 부여하고 있었습니다. 결과:

- **핵심 직관 파괴** — 목표 바로 옆 노드에 h=18, 반대편 끝 노드에 h=2가 붙습니다.
  "목표에 가까울수록 h가 작다"는 휴리스틱의 정의가 화면에서 성립하지 않습니다.
- **A*의 최적성 전제(admissible: h ≤ 실제 남은 거리) 붕괴** — 실측한 표본에서
  목표까지의 길목 노드 전부가 위반이었습니다.

| 노드 | h | 실제 남은 거리 | admissible |
|---|---|---|---|
| 1 (Start) | 18 | 4 | ❌ |
| 3 | 14 | 3 | ❌ |
| 8 | 10 | 2 | ❌ |
| 18 | 9 | 1 | ❌ |

**수정**: 트리상의 실제 거리를 계산한 뒤
- 목표로 가는 길목(조상 사슬) 노드 → 실제 남은 거리를 그대로 부여 (admissible 보장)
- 그 밖의 노드 → 실제 거리의 20~70%로 과소평가

바깥 가지는 자식 방향 간선만 있어 목표에 닿을 수 없으므로(실제 비용 ∞) 어떤 값이든
admissible 합니다. 일부러 작게 잡아 **"가까워 보이는 함정 가지"** 를 만들었습니다.
h만 보는 그리디는 여기에 속고, g를 함께 보는 A*는 덜 속습니다.

검증 (깊이 5 · 자식 최대 3, 20회 시행):

| 항목 | 결과 |
|---|---|
| 길목 노드 admissible 위반 | **0 / 120** |
| 길목 h가 목표에 가까울수록 감소 | **20 / 20** |
| 평균 확장 노드 수 | A* 9.9 vs 그리디 11.1 |
| 그리디가 더 헤맨 트리 | 9 / 20 |
| **A\*가 더 헤맨 트리** | **0 / 20** |

### 🔴 A-2. 그리디에게도 "최적 경로"라고 알려 주고 있었음

성공 메시지가 알고리즘과 무관하게 고정이었습니다.

```javascript
msg: '🎉 목표 노드에 도달했습니다! 최적 경로를 표시합니다.'
```

**이 시뮬레이터가 가르치려는 바로 그 지점을 반대로 가르치고 있었습니다.**
무작위 미로 189회 유효 시행 실측:

| | 결과 |
|---|---|
| 그리디 경로가 A*보다 **긴** 경우 | **31회 (16.4%)** |
| A* 경로가 그리디보다 긴 경우 | **0회** |

즉 6번에 1번꼴로 최단이 아닌 경로를 "최적 경로"라고 표시하고 있었습니다.
(예: A* 19칸 / 그리디 25칸)

**수정**: 알고리즘별로 문구 분리.
- A*: `A*는 g(n)+h(n)을 함께 보므로 이 경로가 최단 경로임이 보장됩니다.`
- 그리디: `다만 그리디는 h(n)만 보고 달려왔기 때문에 이 경로가 최단이라는 보장은 없습니다.`

### ✅ 정확한 부분

- 격자 탭의 h는 **맨해튼 거리**로 올바릅니다. 4방향 이동 · 비용 1 환경에서
  admissible + consistent 이므로 A*의 최적성이 실제로 성립합니다 (189회 시행 위반 0).
- A* / 그리디 분기(`calcF`)가 `g+h` vs `h` 로 정확합니다.
- 목표 도달 판정을 **큐에서 꺼낼 때** 수행합니다(생성 시점이 아니라). A* 정석입니다.
- f 동점 시 h가 작은 노드를 우선하는 tie-breaking이 들어가 있습니다.

### 참고 (미수정)

- 이 엔진은 그리디에서도 더 나은 g를 발견하면 `cameFrom`을 갱신합니다. 순수
  Greedy Best-First보다 경로가 약간 좋아지지만, 위 실측대로 최단 보장은 여전히 없습니다.
- **트리 탭은 구조상 경로 최적성 차이를 보여 줄 수 없습니다.** 자식 방향 간선만 있어
  루트→목표 경로가 유일하므로 두 알고리즘 모두 같은 경로를 냅니다. 트리에서의 차이는
  **확장 노드 수**로만 나타납니다. 최적성 대비는 격자 탭으로 다루는 것이 맞습니다.

## B. 시각화 정합성

### 🔴 B-1. 상태창의 문장이 토막나서 줄바꿈됨 (사용자 제보)

`#grid-status` 요소 **자체가** flex 컨테이너였습니다.

```html
<div class="... h-14 flex items-center justify-center ..." id="grid-status">
```

여기에 `innerHTML`로 `<b>` 가 섞인 문장을 넣으면 텍스트 노드와 `<b>` 가 **각각 별도
flex 아이템**이 되어 따로따로 줄바꿈됩니다. 실제로 아래처럼 깨졌습니다.

```
Step 2: 이웃 노드 탐색    g(n), h(n),    값 갱신 (Open Set
      및                    f(n)              추가)
```

**수정**: 바깥 div는 정렬용으로만 두고 메시지는 안쪽 `<span>`에 넣도록 분리.
`h-14`(고정) → `min-h-14`로 바꿔 두 줄 이상일 때 잘리지 않게 했습니다.

> ⚠️ 같은 패턴(status 요소 자체가 flex + innerHTML에 태그 삽입)은 다른 시뮬레이터에도
> 있을 수 있습니다. 공통 이슈에 등록했습니다.

### ✅ 좋은 부분
- 격자 각 칸에 g / h / f 값을 직접 찍어 주고, 그리디일 때는 g를 숨깁니다.
  "그리디는 g를 아예 안 본다"는 점이 화면에 그대로 드러납니다.
- Open / Closed / Current / Path 4색 구분이 명확합니다.

## C. 안정성 — 상

- 콘솔 에러 **0건**.
- `HeuristicSearch`를 h/g 콜백으로 매개변수화해 트리·격자가 같은 엔진을 공유합니다. 구조가 좋습니다.
- 자동 실행 종료 시 interval 정리가 되어 있습니다.
- 무작위 미로 200회 + 트리 생성 수십 회 반복에도 예외·무한 루프 없음.

### 보강 1건
`generateTree()`가 맨 처음 `resetSearch()`를 호출하는데, 이때 `updateNodeStyle`이
`nodeDataMap.get(id).h`를 무방비로 읽습니다. 트리 재생성이 중간에 끊겨 `nodes`와
`nodeDataMap`이 어긋나면 예외로 화면이 멈춥니다. 가드를 추가했습니다.

  트리 탭 상태창도 `text-sm` → `text-base`.
- 상태창 고정 높이 `h-14` → `min-h-14`. 375px에서 3줄 메시지도 잘리지 않음(부모 102px로 확장, 클리핑 없음).
